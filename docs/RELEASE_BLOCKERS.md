# K&B Management Nexus — release blockers and owner setup

A successful CI build or debug APK is not a production release. The following checks must be completed by the repository/Firebase/Render owner before staff use.

## 1. Render API configuration

The active API is the Render service described by `render.yaml`. Confirm the service is connected to this repository and deliberately deploys the reviewed default-branch code. Auto-deploy is disabled.

Required Render environment values:

- `FIREBASE_SERVICE_ACCOUNT_JSON` — private service-account JSON for Firestore project `kandb-net-sevice`.
- `ADMIN_INITIAL_PASSWORD` — strong initial owner password for K&B ID `Brajraj`.
- `ADMIN_RECOVERY_CODE` — separate strong recovery code.
- `JOB_SECRET` — generated by the Render Blueprint.

Do not put these values in Git, PR comments, screenshots or chat.

## 2. Scheduled attendance and GPS jobs

The default-branch workflow `.github/workflows/backend-keep-alive.yml` wakes the Render API and calls `POST /internal/jobs/tick` every five minutes.

Add GitHub Actions repository secret `K_B_JOB_SECRET` and set it to the exact same value as Render `JOB_SECRET`. If it is missing or mismatched, the scheduled job fails and the GPS grace monitor, automatic checkout and reminders may not run on schedule. The free Render plan may sleep; timing remains best-effort, not guaranteed real-time enforcement.

## 3. Android push notifications

If push notifications are required while the app is fully closed, register Android package `kandbnet.service2010` in Firebase, obtain its `google-services.json`, encode it locally, and add the result as GitHub Actions secret `ANDROID_GOOGLE_SERVICES_JSON_BASE64`. Rebuild and verify a real push on a physical device. Do not upload the file or encoded value to the repository.

## 4. Physical Android GPS acceptance

Complete the checklist in `docs/ANDROID_TRACKING_AND_RELEASE.md` on the actual staff phone models. Verify consent, visible foreground notification, fresh location points with accuracy/timestamps, stale-location handling, GPS loss/restoration, shift end, and that no location is collected outside an active shift.

A compiled APK does not prove background GPS works on a physical device. Android battery optimisation, force-stop, permission revocation, reboot, device shutdown and network loss can interrupt tracking.

## 5. Data migration and backup

Before switching staff or customer records to this app:

1. Back up the existing Firestore data and any legacy AppDeploy records.
2. Reconcile users, customer IDs, plans, payments, attendance and audit history.
3. Verify that the app reads the intended production project.
4. Do not clear or overwrite existing collections during deployment.

## 6. Production Android release

The current APK workflow produces a debug build for internal testing. Create and protect an Android signing key outside this repository before distributing updateable release APKs. Never commit the key or passwords.

## 7. Full application backup and restore

The app currently exports selected finance reports as CSV/PDF; it does not yet provide a full Firestore backup-and-restore workflow. Configure managed Firestore backups with the project owner, or approve a protected encrypted application export design. Do not treat CSV/PDF reports as a complete backup.

## 8. OTA bootstrap and release verification

The first APK built with `@capgo/capacitor-updater` and the splash-screen integration must be installed once. After that, web-only changes can be distributed as OTA bundles. Verify the Render `POST /api/app-updates/check` endpoint, the GitHub OTA release workflow, checksum validation, update-before-work startup behavior and automatic rollback on a real Android device. Native Android/plugin/permission changes still require a package update.
