# Firebase data platform setup for K&B Management Nexus

Firebase is used as the Firestore data platform (and optionally Firebase Cloud Messaging for Android push). The active application API runs on Render and uses Firebase Admin SDK with a private service-account credential.

## Active architecture

- **K&B sign-in:** K&B user ID and password, verified by the Render API. Firebase Authentication is not used for staff/admin login.
- **Database:** Firestore project `kandb-net-sevice`.
- **Backend:** Render service from `render-backend/`; server-side role checks and data access.
- **Client access:** Firestore rules deny direct browser reads/writes. The app uses the Render API.
- **Static hosting:** Firebase Hosting is optional and serves the Vite build only; it does not host the active API.
- **Legacy code:** `functions/` is retained for reference and must not be deployed as a second API.

## Render environment configuration

Configure these values directly in the Render service environment. Never commit them or paste them into source files:

- `FIREBASE_SERVICE_ACCOUNT_JSON`: service-account JSON for the `kandb-net-sevice` project.
- `ADMIN_INITIAL_PASSWORD`: strong initial owner password for the fixed K&B owner ID `Brajraj`.
- `ADMIN_RECOVERY_CODE`: separate strong owner recovery code.
- `JOB_SECRET`: generated by the Render Blueprint and used to protect `POST /internal/jobs/tick`.

The initial owner password and recovery code must be stored securely by the business owner. The server stores password hashes, not plaintext passwords.

## GitHub Actions configuration

Add repository secret `K_B_JOB_SECRET` with exactly the same value as Render `JOB_SECRET`. The scheduled workflow on the default branch uses it to wake the Render service and run attendance, GPS and reminder checks.

For Android push notifications, add `ANDROID_GOOGLE_SERVICES_JSON_BASE64` only after registering the exact Android package `kandbnet.service2010` in Firebase and encoding its `google-services.json` locally. Never commit the JSON file or encoded value.

## Photo/video attachment storage

The current app stores task and complaint attachments as chunked Firestore documents in `task_media` and `complaint_media`. It does not currently use Firebase Cloud Storage for these uploads. Keep this in mind when reviewing Firestore usage and costs. Do not change the storage backend without an owner-approved plan, backup and migration.

## Data safety

1. Confirm the intended Firestore project and region.
2. Export and back up existing collections before migration.
3. Preserve record IDs, user relationships, timestamps and audit history during any import.
4. Do not clear or overwrite existing collections during deployment.
5. Keep Firestore direct-client rules deny-by-default.
